# Масштабирование до 10 000 аккаунтов

Этот документ описывает что меняется в архитектуре когда переходишь с
малых тестовых объёмов (50-500 акк) к боевому масштабу (5000-10000 акк).

## Что вытерпит дефолтный конфиг

| Параметр | Что включено по умолчанию |
|---|---|
| `WORKER_COUNT=10` | 10 шард всего |
| `SENDER_PARALLEL_ACCOUNTS=20` | 20 коннектов одновременно на воркер |
| Без `pgbouncer` | Прямой коннект к Postgres |
| Один сервер | Всё в одном `docker compose up` |
| `optout` слушает всё постоянными коннектами | Polling-режим, но всё равно много |

**Этого хватает** до ~1000 аккаунтов на одном сервере с 16-32 GB RAM.

## С чем сталкиваешься на 1000+

| Проблема | Что происходит |
|---|---|
| **Postgres exhausted** | `max_connections=400` кончаются: каждый воркер держит ~20 коннектов |
| **RAM на коннекты** | 1000 × 40 MB = 40 GB только Telethon-сессии |
| **Один процесс на всё** | GIL, медленный shutdown, тяжёлая отладка |
| **Optout listener** | Persistent коннекты на 1000 акк = вторые 40 GB |

## Решение для 1000-10 000 акк

### 1. PgBouncer (обязательно от 1000+)

В `.env`:
```
USE_PGBOUNCER=true
```

Сгенерировать compose с pgbouncer:
```bash
python scripts/gen_compose.py --shards 100 --senders 10 --pgbouncer
```

PgBouncer держит пул из 50 коннектов к Postgres и мультиплексирует на 2000+ клиентских коннектов. Достаточно для 100 sender-шард.

В нашем `db.py` уже учтена особенность asyncpg + transaction-mode pgbouncer: `statement_cache_size=0`.

### 2. Больше шард

`WORKER_COUNT=100` в `.env` (вместо 10). Тогда:
- На 10 000 акк = 100 акк на шард
- При parallel=20 на воркер — 20 коннектов одновременно × 100 шард = 2000 connections
- 2000 × 40 MB = 80 GB RAM (всё ещё много, см. ниже про сервера)

### 3. Многошардовые sender-процессы

Не обязательно поднимать 100 контейнеров. Один процесс может вести несколько шард через asyncio:

```bash
python -m src.sender --shards 0-9    # этот процесс ведёт шарды 0,1,2,...,9
```

Скрипт `gen_compose.py` сам распределяет шарды между sender-N контейнерами поровну.

### 4. Polling-based optout

Уже встроено в `src/optout.py` — не держит persistent connections.
Раз в `OPTOUT_POLL_INTERVAL_SECONDS` (10 мин) подключается к каждому акк,
проверяет unread, отключается.

10 000 акк × 1 цикл / 10 мин = 17 polls/сек, манагеабельно.

Шардить optout по тому же принципу:
```bash
python -m src.optout --shards 0-9   # poll только свои 1000 акк
```

В compose дефолтном — `--shards all`, что норм до ~2000. Дальше шардь по
несколько процессов.

## Сервер: один или несколько

### Один большой сервер (до ~5000 акк)

| Что | RAM | Кол-во |
|---|---|---|
| Postgres + PgBouncer | 4-8 GB | 1 |
| 10 sender-контейнеров × 10 шард | 60 GB (1000 коннектов) | 10 |
| optout × 1 контейнер | 2-4 GB (polling) | 1 |
| intake API | 0.5 GB | 1 |
| **Итого** | **~80 GB** | 12 |

Сервер: **128 GB RAM, 32 vCPU, 200 GB SSD**. Бюджет: ~$200-400/мес (Hetzner CCX63, Aeza Pro).

### Несколько серверов (5000-10000+ акк)

При >5000 акк один сервер становится bottleneck — RAM, сеть, IO Postgres.
Распределение:

**Сервер 1 (Database):**
- Postgres + PgBouncer
- 16 GB RAM, 8 vCPU, 200 GB SSD

**Серверы 2-N (Senders):**
- На каждом ~30-50 GB RAM, 16 vCPU
- Каждый ведёт диапазон шард (см. `--shard-offset` в gen_compose.py)
- Подключаются к Postgres по сети (нужен внутренний VPC/private network)

**Пример — 2 sender-сервера для 100 шард:**

На server2:
```bash
python scripts/gen_compose.py --shards 100 --senders 5 --pgbouncer \
    --shard-offset 0 --shard-range 50      # шарды 0-49
```

На server3:
```bash
python scripts/gen_compose.py --shards 100 --senders 5 --pgbouncer \
    --shard-offset 50 --shard-range 50     # шарды 50-99
```

В `.env` на обоих серверах:
```
POSTGRES_HOST=server1.internal     # или PgBouncer-server
USE_PGBOUNCER=true
PGBOUNCER_HOST=server1.internal
```

**Optout сервер (отдельный, опц.):**

10к polling нагружает мало, но если хочется изолировать — поднять отдельно:
```bash
docker compose up -d optout
```
(только optout-сервис на отдельной машине, тогда из `gen_compose.py` убирать sender'ы)

## Бюджет на 10к акк

| Статья | $/мес |
|---|---|
| 1× DB сервер 32GB | $40 |
| 3× Sender сервера 64GB каждый | $360 |
| Inter-server трафик | $0 (приватная сеть провайдера) |
| **Инфра итого** | **~$400/мес** |
| Прокси (если включаешь PROXIES_ENABLED) | $1500-7500/мес |
| Anthropic API (у нас не используется) | $0 |
| Аккаунты (амортизация ~5% отвал) | $5000-10000/мес |

Прокси и аккаунты — главные статьи, не инфра.

## Реалистичные RPM на 10к акк

| Параметр | Значение |
|---|---|
| Сообщений/акк/час | 60 (одно в минуту в среднем) |
| Сумма по всему пулу | 600 000 msg/час пиково |
| Реально с FloodWait и cooldowns | ~300 000 msg/час |
| Активное окно 14ч/сутки | ~4 200 000 msg/день потолок |

При среднем 200 контактов на акк = 2 000 000 контактов суммарно.
**Полная рассылка по всем — за половину дня.**

Дальше упирается в:
- Антифрод Telegram (главное)
- Конверсию (open rate / reply rate)
- Стоимость новых аккаунтов

## Контрольный список перехода

Когда твой парк перерастает 1000 акк:

- [ ] `WORKER_COUNT` поднять до 50-100
- [ ] `USE_PGBOUNCER=true` + перегенерить compose
- [ ] Хостинг апгрейд до 64+ GB RAM
- [ ] Мониторить `make psql` запросом stats — нет ли застрявших драфтов
- [ ] Проверить что optout успевает за свой цикл (10 мин) на твоём парке
- [ ] План резервных аккаунтов: 5-10% отвал в месяц требует постоянного intake

Когда >5000:

- [ ] Развернуть multi-server (DB отдельно, senders на 2-3 машинах)
- [ ] Внутренний VPC между серверами
- [ ] Backup Postgres в отдельный storage каждый час
- [ ] Алерты в Telegram-бот (TODO в проекте, если потребуется — добавить)

## Что НЕ масштабируется автоматически

Эти штуки придётся ручками тюнить:

1. **Postgres `max_connections`** — увеличить с 400 до 800 при >100 шард
2. **`shared_buffers`** в Postgres — 25% от RAM сервера
3. **`SENDER_PARALLEL_ACCOUNTS`** — снизить если RAM не хватает, повысить если CPU простаивает
4. **`OPTOUT_POLL_INTERVAL_SECONDS`** — увеличить с 600 до 1800 при 10к (один цикл одного шарда занимает дольше)

Все эти ручки в `.env`.
